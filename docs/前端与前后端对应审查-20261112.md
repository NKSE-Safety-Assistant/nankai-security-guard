# 三角色后台与前后端对应审查

日期：2026-11-12。

范围：管理员、编辑员、审核员页面；共享工作台脚本与样式；学生端发布内容读取；Node.js 接口与 MySQL 适配层。

本轮执行只读代码审查、本机 HTTP 检查、隔离函数复现及现有测试。没有修改业务代码、数据库、账号或线上部署。

## 结论

三个角色页已有真实接口及数据读写实现，主要字段可以对应，但尚不能判定完整联调通过。发现访问控制、案例撤回同步、侧栏交互、前后端校验等确定问题。应先修复功能和权限，再统一视觉与状态。

## 已确认问题与优先级

| 编号 | 优先级 | 问题及影响 | 证据 | 建议 |
|---|---|---|---|---|
| A01 | P0 | 静态资源服务没有限制私有文件，本机未登录请求可以读取环境配置及账号文件；若服务对外可达，这些内容也存在被读取的风险 | `/.env`、`/data/admin-accounts.json` 均返回 HTTP 200；未在报告记录文件内容。server.js:2012、2020 | 采用静态文件白名单或独立 public 目录；禁止配置、账号、日志、备份及服务源码被下载；对已对外暴露的凭据另行更换 |
| A02 | P0 | 账号停用、角色移除后，旧会话仍能通过原权限校验 | sessionRoles 将旧 cookie 权限保留并合并数据库权限；隔离复现中 paused 账号及移除 reviewer 角色的账号仍通过 reviewer 校验。server.js:104、117 | 每次后台请求以数据库启停状态和当前角色为准；必要时增加会话版本和失效机制 |
| A03 | P1 | 案例查询对学生与工作人员返回同一整份数据库对象，缺少按角色的数据裁剪 | 当前开发模式下，未登录 GET /api/cases 返回 25 案例、其中 13 未发布，并包含 4 条后台用户记录；正式模式下学生通过 any 身份检查后仍走同一响应。server.js:1757、1762 | 学生只取已发布案例必要字段；后台案例接口限定编辑/审核角色；任何案例响应不附带用户列表 |
| A04 | P1 | 编辑员、审核员点击侧栏状态会报错，可能只改变选中样式而未更新案例内容 | 两页调用不存在的 renderCaseList；实际渲染函数为 renderReviewList。隔离执行两个点击处理器均得到 ReferenceError。editor.html:173；reviewer.html:145 | 统一状态切换入口、清理选中案例和搜索状态，侧栏与正文状态标签共用同一逻辑 |
| A05 | P1 | 后台撤回案例后，学生端可能仍显示该案例 | app.js 无论接口是否成功都合并静态案例；隔离测试中实时接口返回空、静态库保留已发布案例，最终仍生成该场景。app.js:576 | 后端可用时以实时接口为准；静态库仅在明确演示模式或接口不可用时使用，并标明数据来源 |
| A06 | P1 | 审核页自动检查通过不代表后端允许发布 | 隔离样例中前端五项全部通过，但后端拒绝缺少脱敏材料、情景开端和风险升级。reviewer.html:415；server.js:805 | 统一规则；建议由后端提供检查结果，前端提供字段定位和说明；显示全部失败原因 |
| A07 | P1 | 部分审核列表及已发布案例模板直接将案例文本插入 innerHTML，存在把文本当 HTML 解析的风险 | reviewer.html:301 直接插入 item.title 等字段；已发布浏览模板也有类似拼接 | 所有外部/编辑内容使用 textContent 或统一转义，并对链接协议单独校验；本轮未执行注入载荷 |
| A08 | P2 | 前端和 API 允许合格分为 0，数据库写入时却变为 80 | db-adapter.js:529 使用 task.passScore || 80；隔离捕获 SQL 确认输入 0 实际生成 80 | 使用空值默认而非真假值默认；为边界值增加契约验证 |
| A09 | P2 | 接口失败被转换成“没有案例”，用户可能误以为数据已丢失 | initAdminCases 把接口错误写入 .admin-empty，case-workspace.js:44 将所有 .admin-empty 改写成正常空队列 | 区分加载、正常空、筛选无结果、未登录、无权限和接口故障；故障保留具体提示与重试入口 |
| A10 | P2 | 新批准案例不一定能在学生端找到 | app.js:603 固定截取排序后的 10 个情景，无后续分页/查看全部入口 | 消防置顶作为展示排序规则保留；完整案例库提供分页或全部场景入口，不能用展示数量上限代替完整发布结果 |
| A11 | P2 | 角色数据支持逗号分隔的多角色，而后台表单只能编辑单一角色 | sessionRoles 支持多个角色；admin.html:181 把原始 role 填入只有三个单选项的 select；保存 API 仅接受单一角色 | 明确单角色或多角色产品规则；如保留多角色，表单、接口与数据库更新规则统一 |
| A12 | P2 | 编辑防丢失提示覆盖不全，普通保存不保存备注 | staff-workspace.js 仅跟踪 #caseEditForm 内 input；#reviewNote 在表单外。saveEditorForm 不含 reviewNote，而提交时才附加 | 明确备注的保存动作；统一记录所有编辑字段和程序赋值，提供保存状态；长表单可增加草稿机制 |

P0 为对外部署前应优先修复的问题；P1 为影响核心业务或访问边界的问题；P2 为准确性、流程和体验问题。

## 前端进一步优化建议

1. 将正常空列表与错误状态分开，提供就地重试，不把所有错误统一归因于数据库。
2. 管理员抽屉应使用明确的请求成功/失败结果，不凭旧 state.task.id 推断成功；重复打开同一任务且请求失败时可能只剩空白详情。
3. 统一弹窗和抽屉的 Escape、焦点约束、关闭后焦点恢复以及未保存确认；当前只覆盖了任务详情抽屉。
4. 新建任务、保存授权、案例保存与审核操作统一防重复点击，并区分“保存成功、重新加载失败”和“保存失败”。
5. 已发布案例库完善标题/类型/来源转义、搜索与返回后状态保留；搜索目前按键重建列表并强行恢复焦点，需检查中文输入。
6. 原文自身已是 details，增强脚本再次包裹 details，产生两层折叠；合并成一层即可。
7. 表格范围应压缩显示并可展开；固定 10 条场景及硬编码年级不适合作为长期管理规则。
8. CSS 存在基础样式、共享覆盖、角色覆盖三层；JS 使用运行时重写函数、移动表单节点、MutationObserver 增强。应逐步整理成明确的页面组件与状态入口，减少选择器覆盖和时序问题。
9. 统一标题、正文、辅助说明和按钮字重；在真实浏览器核对字体实际命中情况，不能仅凭 CSS 声明判断一致。

## 本轮验证记录及限制

- 本机健康接口正常，数据库模式为 MySQL，当前关闭强制飞书登录（开发演示模式）。
- 未登录访问管理员统计接口返回 401，说明后台接口有登录保护。
- 新增工作台 CSS/JS 地址均返回 HTTP 200。
- 已复现：两个侧栏点击 ReferenceError、停用账号/移除角色旧会话仍有权限、0 分写成 80、审核前后端校验不同、撤回案例从静态库重新出现。
- `npm test` 全部通过；新增三个工作台脚本语法检查通过。这些测试不能覆盖上表所有问题，因此不能作为完整验收结论。
- 没有创建任务、提交案例、修改权限、执行真实撤回或修改现有数据；没有生成或伪造后台登录状态。
- 本轮没有完成真实三角色会话下的全部操作、桌面与移动截图验收，也没有验证飞书独立服务器的运行状态。

## 建议处理顺序

1. 关闭私有文件访问、按角色裁剪案例接口、修复账号停用与角色撤销。
2. 修复侧栏状态切换及案例撤回同步。
3. 统一前后端校验、默认值和文字安全输出。
4. 修复保存、错误、未保存及弹窗状态，再收敛字体、密度与响应式。
5. 使用隔离测试数据走完“发布任务—学生答题—统计”和“编辑—提交—退回—再提交—发布—撤回”，最后更新数据库交接文件并部署。
